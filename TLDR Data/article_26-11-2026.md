DEEP DIVES

 WHERE AGENTS MEET THE BROWSER: BUILDING A BROWSER-NATIVE AGENT (17
MINUTE READ) [6]

 LinkedIn built an internal AI agent that works across tools in
employees' existing Chrome sessions, turning incident threads into
tickets and documents into slide decks. It uses structured page data
to cut token usage and tool-specific playbooks to improve reliability,
while showing its actions and linking to evidence so users can verify
the work.

 HOW GRAB BUILT SCARLET: THE AI TEAMMATE THAT TURNS A SLACK MESSAGE
INTO A PRODUCTION DATA PIPELINE (13 MINUTE READ) [7]

 Grab's AI agent, Scarlet, turns Slack messages and Jira tickets into
data pipeline changes, checks the resulting data against production,
and opens merge requests for engineers to review. After Grab
introduced reusable, team-specific instructions and automated data
checks, the share of Scarlet's merge requests that engineers merged
rose from about 50% in May to over 85% in September.

 DISTRIBUTED PRIMARY KEYS (44 MINUTE READ) [8]

 Reproducible benchmarks compare primary key strategies for
multi-region PostgreSQL across index size, WAL overhead, and failover
safety. UUIDv7 is efficient and needs no coordination. Regional
sequences can collide after failover, timestamp-based IDs are
vulnerable to clock rollback, and composite keys simplify replication
filtering but use more storage.

 BACKFILLING TENS OF BILLIONS OF ROWS NEXT TO LIVE LOGICAL REPLICATION
(PART 2) (10 MINUTE READ) [9]

 A live PostgreSQL migration moved tens of billions of rows using
parallel COPY, fixed ID ranges, and resumable checkpoints. Broken WAL
archiving filled the target's disk, while subscription lag retained
WAL on the source until streaming = parallel cleared the backlog.
Missed updates and costly joins showed why reconciliation needs checks
for both correctness and performance.

OPINIONS & ADVICE

 5 LESSONS IN AI CONTEXT ENGINEERING: WHY MORE CONTEXT IS NOT BETTER
(10 MINUTE READ) [10]

 Salesforce's Help Agent must work out what a customer owns and is
entitled to, with lookups under 200 milliseconds at the median. More
data was not the answer. The team resolves relationships, business
rules, and access ahead of time into Data 360 data graphs served by
one lookup. Warehouse views had taken 7 to 30 seconds for one scoring
workload.

 LEGIBLE FIRST: HOW T2 BUILT AI ON WHAT IT ALREADY OWNED (5 MINUTE
READ) [11]

 T2 Tea consolidated data from 14 systems into one warehouse and built
a semantic layer with 243 metrics, letting off-the-shelf AI models
retrieve only the data and business rules each question needs. T2
reports spending about A$30 per seat per month and completing a
channel analysis in about an hour that previously took consultants
weeks.

 UNCLEAN LEADER ELECTION: KAFKA TROLLEY PROBLEM WHERE YOU ALWAYS END
UP PULLING THE LEVER (5 MINUTE READ) [12]

 When no in-sync replica remains available, Kafka can sacrifice
durability to restore availability by electing an out-of-sync replica,
potentially losing acknowledged writes. Kafka 4.0's Eligible Leader
Replicas (ELR) can avoid this trade-off in certain failure scenarios.
The decision to prioritize availability over durability should be made
at the topic level, based on business requirements, rather than during
an outage.

 ORDERBOOK-LAKEHOUSE (GITHUB REPO) [14]

 Orderbook Lakehouse is a fully local, Docker-based reference
architecture for incremental market-data processing using Apache
Iceberg, Apache Polaris, Spark (Scala), Redpanda Connect, and
SeaweedFS. HTTP events flow through Bronze, Silver, and Gold Iceberg
tables to produce order-book state and trading analytics. Iceberg
snapshots enable incremental processing and idempotent recovery, while
Polaris coordinates atomic metadata commits. The architecture
demonstrates reliable, restartable lakehouse pipelines without managed
cloud infrastructure.

 POLARS 2.2 BRINGS OUT-OF-CORE JOINS AND SQL-NATIVE ICEBERG OPERATIONS
(9 MINUTE READ) [15]

 Polars 2.2 extends its streaming engine with disk-spilling
equi-joins, allowing datasets larger than available RAM to be
processed without exhausting memory. SQL gains INSERT, UPDATE, DELETE,
and COPY, alongside native Iceberg table writes and maintenance
operations. A new scan_database API and over 100 performance
improvements further strengthen Polars as a single-node analytical
engine for production data pipelines.

 HARDWOOD 1.1 ADDS PARALLEL PARQUET WRITES, S3 SUPPORT, AND ALP
ENCODING (7 MINUTE READ) [16]

 Hardwood, the lightweight, dependency-free Parquet library for the
JVM, introduces parallel file writing and direct S3 uploads with
multipart support. The release candidate adds ALP encoding for more
compact floating-point storage, field IDs for lakehouse
interoperability, and a redesigned read scheduler delivering up to
1.8× faster full scans than Hardwood 1.0. These improvements position
Hardwood as a high-performance alternative for JVM applications that
need direct Parquet access without Hadoop dependencies.

 DBT EVALS: OUR FIRST FORAY INTO DATA AGENT MANAGEMENT (8 MINUTE READ)
[17]

 dbt Evals is a framework that asks analytics agents the same
questions across multiple runs and checks their answers with SQL
tests, classifiers, or LLM judges. The goal is to catch accuracy
regressions when data models or metrics change, though the initial
design tests a configurable stand-in for the production agent.

 COMPACTION WAS ON. IT NEVER RAN. (10 MINUTE READ) [18]

 Benchmarking DuckDB-based duckgate against Athena exposed a
small-file problem: DuckDB was up to 25x slower on an Iceberg table
containing just 440K rows spread across thousands of tiny Parquet
files. Hourly partitioning created excessive fragmentation, while AWS
Glue compaction was enabled but never executed. DuckDB 2.0's
asynchronous remote Parquet I/O narrowed the performance gap to
roughly 4×, but the fundamental lesson remains: table layout and
effective maintenance can matter more than query engine selection.
